### 1. C# app on Linux vs. the direct CLI invocation: counts and `.obj` identical under `-d` — **met**

**The CLI.** The GUI CLI does not configure with the toolbox's CMake 4.x (M1 Open #2), so I
built it the way M1 did, with CMake 3.31.10 from the venv, into the git-ignored `build/`:

```
toolbox run -c instant-meshes-build bash -c '~/.cache/im-cmake3/bin/cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && ~/.cache/im-cmake3/bin/cmake --build build --target "Instant Meshes"'
```

109/109 steps, rc 0, 0 lines matching `^FAILED|error:`. I also built the **pre-M1 baseline
CLI** (`05138b8`, from `git archive`, with the same submodule checkouts symlinked in) in
`/tmp/im_base/build`, with `-DCMAKE_CXX_FLAGS=-Wno-changes-meaning`, also rc 0. The plan's
stated purpose is to check "that the M1 `batch_process` refactor didn't change behavior",
and comparing against the pre-refactor binary tests that directly.

**The comparison.** I ran
`toolbox run -c instant-meshes-build csharp-demo/compare_with_cli.sh <CLI> <input> <dir>`
for both CLIs, on two inputs. One input is the welded source that M3/D8 tuned on
(`tuning_runs/source_welded.obj`, regenerated by `tune_params.make_welded_source()`, sha256
`b63990bc…`, the same as the one M3 logged). The other is the raw `source.obj`. Every
comparison came out identical:

| CLI binary | input | C# `out_vertex/face_count` | CLI written V/F | `.obj` bytes | sha256 of both outputs | scorer aggregate (both) | candidate metrics |
|---|---|---|---|---|---|---|---|
| current (`HEAD`) | welded | 11355 / 11415 | 11355 / 11415 | identical | `fd857df8…` | 0.1461292849353033 | identical |
| pre-M1 `05138b8` | welded | 11355 / 11415 | 11355 / 11415 | identical | `fd857df8…` | 0.1461292849353033 | identical |
| current (`HEAD`) | `source.obj` | 11551 / 9908 | 11551 / 9908 | identical | `7411eab1…` | 0.1786561965752647 | identical |
| pre-M1 `05138b8` | `source.obj` | 11551 / 9908 | 11551 / 9908 | identical | `7411eab1…` | 0.1786561965752647 | identical |

There is a third, independent agreement. On the welded input, the output sha256 `fd857df8…`
and the aggregate 0.1461292849353033 are exactly what M3 logged for trial `v2799_coff_s1`
through ctypes (`tuning_results.jsonl`). So the C#, Python-ctypes, current-CLI and
pre-refactor-CLI paths all produce the same bytes.

Run time: ~28 s per `compare_with_cli.sh` invocation. Most of that is the two scorer runs;
each remesh takes ~4–5 s.

**Negative control.** The comparison can fail. The demo with `--smooth 2` on the welded
input reports the **same** V/F (11355/11415), but its `.obj` differs from the CLI's `-S 1`
output (`cmp`: differs at byte 8). So comparing counts alone would not have caught a
parameter-marshalling bug in `smooth_iter`; the byte comparison does.

## What I got wrong on the way

- The first `.csproj` had `dotnet run -- [options]` in an XML comment. `--` is illegal inside
  XML comments, so MSBuild refused to load the project (MSB4025). Fixed before the commit.
- I first mapped `-i` to `--input`. The CLI's `-i` is `--intrinsic`, and the CLI takes its
  input as a positional argument. I made `-i` mean intrinsic (as in the CLI) and left the
  input as `--input` only, so a CLI command line's flags mean the same thing here.
- I expected comparing V/F counts to be a reasonable first-line parity check. The negative
  control shows it is not: `smooth_iter` 1 vs. 2 gives identical counts. Only the byte/sha
  comparison is meaningful.

## Open

1. **Windows `.dll` validation — explicitly open, not done.** It needs a Windows machine or
   CI runner with VS and the .NET 8 SDK:
   - `cmake -S . -B build-core -G "Visual Studio …" -A x64 -DIM_CORE_ONLY=ON`, then
     `cmake --build build-core --config Release --target instantmeshes_core` (output
     `build-core/Release/instantmeshes_core.dll`, which the `.csproj` picks up);
   - `dotnet build csharp-demo` and `dotnet run --project csharp-demo -- --smoke-test`;
   - for parity, the Windows CLI with `-d -t 1 -v 2799 -S 1` on the welded source, compared
     with `fc /b`. The expected sha256 is not necessarily the Linux `fd857df8…`, because
     MSVC floating point can differ from GCC's. What must hold is C# = CLI *on the same
     platform*.
   - This also closes M1 Open #1 (MSVC build never proven) and the unresolved MinGW+Wine
     TBB crash on the first real remesh. If that crash is real on MSVC, the smoke test
     will hit it.
   - `compare_with_cli.sh` is bash. On Windows it needs Git Bash/WSL, or a manual run of
     the same steps.
2. **The demo does not weld.** D8's parameters were tuned on the welded source. The plan
   says to run on `source.obj`, which is the default input. `--input
   tuning_runs/source_welded.obj` reproduces M3's result, and the README says how to write
   that file. I did not port the weld to C#: it would be a third implementation of
   `tune_params.weld()`, and the plan asks for a minimal app. If the demo is meant as the
   end-user entry point, a C# weld (or a weld in the native library) is the next step.
3. The `csharp-demo` check depends on an already-built `build-core/libinstantmeshes_core.so`
   (above). Adding the M1 cmake steps to the check's command, as `tuning-sweep` does, would
   make it self-contained. That is the owner's manifest, so I did not change it.
4. The GUI CLI still only builds with CMake < 4 (M1 Open #2). The parity check depends on
   the venv `~/.cache/im-cmake3`.
5. Earlier open items stand: M1 #3–5 (Eigen soft dependency, re-entrancy, `Optimizer`
   thread join), M2's (reverse fidelity, distance-query speed), and M3's (nobody has looked
   at the D8 mesh).
